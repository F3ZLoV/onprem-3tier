# 학습 노트 — 내가 만든 것을 내 말로 설명하기

이 문서는 다른 사람에게 보여주기 위한 것이 아니라, **내가 이해하기 위한 것**이다.
지금까지 명령어를 따라 치면서 만든 시스템이 실제로 무엇인지, 왜 그렇게 만들었는지를 쉬운 말로 정리한다.

각 장 끝에는 "확인 질문"이 있다. 정답을 맞히는 게 목적이 아니라, **막히는 지점을 찾는 게 목적**이다. 막히면 그 부분을 다시 읽으면 된다.

---

## 0장. 내가 만든 게 뭔지 한 문장으로

> **"사람들이 주소 하나로 웹사이트에 접속하면, 뒤에서 서버 여러 대가 알아서 일을 나눠 받고, 서버 한 대가 고장 나도 사람들은 모르게 계속 돌아가는 시스템."**

여기에 데이터베이스까지 붙여서, 데이터도 두 곳에 자동으로 복사되게 만들었다.

### 왜 이런 걸 만드나

서버가 한 대뿐이면, 그 한 대가 고장 나는 순간 서비스가 멈춘다. 쇼핑몰이라면 결제가 안 되고, 회사라면 업무가 마비된다.

그래서 실무에서는 **"한 대가 죽어도 괜찮게"** 만든다. 이걸 **이중화**라고 한다. 이 프로젝트는 그걸 직접 만들어 본 것이다.

## 1장. 서버 7대가 각각 뭘 하나

가상머신(VM) 7대를 만들었다. 각각 역할이 다르다.

| 서버 | 주소 | 하는 일 | 비유 |
|---|---|---|---|
| ansible | .10 | 나머지 서버들에게 명령을 내림 | 감독 |
| VIP | .20 | **가짜 대표 주소** (실제 서버 아님) | 회사 대표 전화번호 |
| lb1 | .21 | 손님을 받아서 웹서버에 나눠줌 | 안내데스크 A |
| lb2 | .22 | lb1이 죽으면 대신 받음 | 안내데스크 B |
| web1 | .31 | 실제로 웹페이지를 보여줌 | 직원 1 |
| web2 | .32 | 실제로 웹페이지를 보여줌 | 직원 2 |
| db1 | .41 | 데이터를 저장 (원본) | 장부 원본 |
| db2 | .42 | db1의 데이터를 복사해서 보관 | 장부 사본 |

### 손님이 웹사이트에 접속하면 무슨 일이 일어나나

1. 손님이 **대표 주소(.20)** 로 접속한다. 손님은 이 주소만 안다.
2. 그 주소를 **지금 들고 있는 안내데스크(lb1)** 가 요청을 받는다.
3. lb1이 **일 안 바쁜 직원(web1 또는 web2)** 에게 넘긴다.
4. 그 직원이 웹페이지를 만들어서 손님에게 준다.
5. 데이터가 필요하면 **장부(db1)** 를 본다.

### 여기서 핵심 아이디어

**손님은 web1이나 web2의 주소를 절대 모른다.** 대표 주소(.20)만 안다.
왜냐면 — 만약 손님이 web1 주소를 직접 알고 접속하면, web1이 죽는 순간 그 손님은 끝이기 때문이다.
대표 주소만 알면, 뒤에서 무슨 일이 일어나든(서버가 죽든 바뀌든) 손님은 영향을 안 받는다.

### 확인 질문
- 손님이 web1 주소(.31)를 직접 알고 접속하면 어떤 문제가 생기나?
- VIP(.20)는 왜 "가짜" 주소인가? 실제 서버가 아닌데 어떻게 접속이 되나?

## 2장. Ansible — 왜 명령어를 직접 안 치고 코드로 만드나

### 문제 상황

서버가 7대다. 각 서버에 웹서버 프로그램을 깔려면?
- 서버 1에 접속 → 설치 → 설정 → 방화벽 열기 → 실행
- 서버 2에 접속 → 설치 → 설정 → 방화벽 열기 → 실행
- ... 7번 반복

7번 반복하면 실수가 난다. 그리고 6개월 뒤 "이거 어떻게 만들었더라?" 하면 기억이 안 난다.

### Ansible이 하는 일

**"할 일을 파일에 적어두면, 여러 서버에 한 번에 실행해준다."**

```bash
ansible-playbook web.yml
```

이 한 줄로 web1, web2에 동시에 nginx가 설치되고 설정되고 실행된다.

### 멱등성 — 이 프로젝트에서 계속 나온 단어

**"몇 번을 실행해도 결과가 같다"** 는 뜻이다.

실행 결과에서 이런 걸 봤을 것이다:
```
ok=6    changed=5
```

- **changed**: 실제로 뭔가 바꿨다 (설치 안 돼 있어서 설치함)
- **ok**: 확인해보니 이미 돼 있어서 아무것도 안 함

두 번째로 같은 명령을 실행하면 대부분 `ok`가 되고 `changed=0`이 된다. 이미 다 돼 있으니까.

**왜 이게 중요한가:** 일반 스크립트는 두 번 실행하면 꼬인다(같은 걸 또 설치하려다 에러). Ansible은 "이미 됐으면 건너뛰기"를 하니까 안전하게 몇 번이고 돌릴 수 있다.

### 용어 3개만 기억하면 된다

| 용어 | 뭐냐면 | 우리 프로젝트에서 |
|---|---|---|
| **인벤토리** | 관리할 서버 명단 | `inventory/hosts.ini` — web1, web2, lb1... 적어둔 파일 |
| **플레이북** | "어느 서버에 무슨 일을 할지" 적은 대본 | `web.yml`, `lb.yml`, `db.yml` |
| **롤(role)** | 할 일을 묶어둔 꾸러미 | `roles/nginx/` — nginx 설치+설정+방화벽+실행 세트 |

플레이북이 "web 서버들에 nginx 롤을 적용해라"라고 지시하면, Ansible이 인벤토리에서 web 서버들을 찾아 롤에 적힌 일을 한다.

### 확인 질문
- 같은 플레이북을 두 번 실행하면 왜 안전한가?
- 인벤토리, 플레이북, 롤은 각각 무슨 역할인가?

## 3장. 로드밸런서 — 일을 나눠주는 안내데스크

### 로드밸런서(HAProxy)가 하는 일 두 가지

**① 나눠주기 (분산)**
요청이 오면 web1, web2에 번갈아 보낸다. 한 서버에만 몰리지 않게.

우리가 확인한 방법:
```bash
for i in $(seq 1 10); do curl -s http://192.168.56.20 | grep "Served by"; done
```
결과가 web1, web2, web1, web2... 이렇게 번갈아 나왔다.

> 브라우저에서 새로고침할 땐 잘 안 바뀌었는데, 그건 브라우저가 한 번 연결한 걸 재사용해서다(keep-alive). curl은 매번 새로 연결해서 정확하게 보인다.

**② 죽은 서버 빼기 (헬스체크)**
로드밸런서가 주기적으로 web1, web2에 "살아있어?"라고 물어본다.
web1이 대답을 안 하면 → 목록에서 빼고 web2로만 보낸다.

우리가 확인한 방법: web1의 nginx를 끄니까, HAProxy 상태 화면(`:8404/stats`)에서 web1이 빨갛게 변하고, curl은 web2만 응답했다. **손님은 아무것도 몰랐다.**

### 그런데 로드밸런서가 죽으면?

여기서 문제가 생긴다. 웹서버는 이중화했는데, **로드밸런서가 한 대면 그게 죽으면 전부 끝이다.**

그래서 로드밸런서도 2대(lb1, lb2)로 만들었다. 그런데 2대면 손님은 어느 주소로 접속해야 하나?

### VIP — 가짜 주소를 서로 주고받기

**해결책: 주소 하나(.20)를 두 대가 번갈아 들고 있게 한다.**

- 평소: lb1이 .20을 들고 있음 (손님 요청이 lb1로 감)
- lb1이 죽으면: lb2가 .20을 가져감 (손님 요청이 lb2로 감)
- 손님은 계속 .20만 보니까 **아무것도 모른다**

이걸 **VIP(가상 IP)** 라고 하고, 주소를 주고받는 프로그램이 **Keepalived**다.

### 어떻게 "죽었는지" 아나

lb1이 1초마다 "나 살아있어!"라고 신호를 보낸다. lb2는 그걸 듣고 있다.
신호가 3초쯤 안 오면 → lb2가 "죽었구나" 하고 주소를 가져간다.

실제로 우리가 측정했을 때 **끊긴 시간은 약 1초**였다. (1초마다 curl을 날리는 루프를 돌려놓고 lb1을 죽였더니, 딱 한 번 실패하고 바로 복구됐다)

### 우리가 겪은 사고: 양쪽이 동시에 주소를 가져감

처음 설정했을 때, **VIP가 lb1과 lb2 양쪽에 다 붙어있었다.**

원인: 방화벽이 "나 살아있어!" 신호를 막고 있었다.
→ 서로의 신호를 못 들음 → 각자 "상대가 죽었네?" 착각 → 둘 다 주소를 가져감

이걸 **split-brain**(뇌가 둘로 갈라짐)이라고 부른다.

해결: 방화벽에서 그 신호(VRRP)를 허용했다. 이 신호는 일반적인 방식으로는 안 열려서 특별한 규칙이 필요했다.

### 확인 질문
- 웹서버 이중화(헬스체크)와 로드밸런서 이중화(VIP)는 각각 무슨 문제를 푸는가?
- split-brain은 왜 일어났나?

## 4장. 데이터베이스 복제 — 장부를 두 권 만들기

### 왜 DB를 두 대로 나누나

데이터베이스가 한 대인데 그게 고장 나면, **데이터가 날아간다.** 서버는 다시 만들면 되지만 데이터는 못 만든다.

그래서 db1(원본)에 저장되는 내용을 db2(사본)에 **자동으로 계속 복사**한다.

### 어떻게 복사되나

1. db1에 데이터를 넣으면, db1은 "무엇이 바뀌었는지"를 기록한다 (**WAL**이라는 변경 기록)
2. db2가 db1에 접속해서 그 기록을 **실시간으로 받아온다**
3. db2가 받은 기록대로 자기 데이터도 똑같이 바꾼다
4. 결과: db2는 db1과 거의 같은 내용을 갖게 된다

우리가 확인한 방법:
```
db1에서: CREATE TABLE repltest → INSERT (1, 'hello from db1')
db2에서: SELECT * FROM repltest → 1 | hello from db1  ← 자동으로 나타남!
```
**db2에는 아무것도 안 넣었는데 db1 데이터가 나타났다.** 이게 복제가 작동한다는 증거다.

### db2는 읽기만 된다

db2는 db1을 따라하는 역할이라, db2에 직접 쓰기는 안 된다(읽기 전용).
확인 방법: `SELECT pg_is_in_recovery();` → `t`가 나오면 "나는 사본입니다"라는 뜻.

### 데이터를 별도 디스크에 저장한 이유

DB 데이터를 운영체제와 같은 공간에 두면, 데이터가 커져서 공간을 다 채우면 **운영체제 자체가 멈춘다.**

그래서 5GB짜리 디스크를 따로 붙여서 DB 데이터 전용으로 만들었다. 데이터가 꽉 차도 운영체제는 멀쩡하고, 나중에 디스크만 더 붙이면 공간을 늘릴 수 있다. (이 방식을 **LVM**이라고 한다)

### 확인 질문
- db1에 넣은 데이터가 db2에 나타나는 걸 어떻게 확인했나?
- DB 데이터를 왜 별도 디스크에 뒀나?

## 5장. 이번에 크게 고생한 것 두 가지

### 사고 1. 설정은 맞는데 안 먹히던 문제 (이틀 걸림)

**상황:** db2가 db1에 접속하려는데 계속 "권한 없음"으로 거부당했다. 접속 허용 설정 파일(`pg_hba.conf`)에는 분명히 허용한다고 적혀 있었다.

**어떻게 찾았나 — 하나씩 지워나가기**

이게 이 프로젝트에서 배운 가장 중요한 방법이다. **의심되는 걸 하나씩 없애면서 범위를 좁힌다.**

| 의심 | 어떻게 확인 | 결과 |
|---|---|---|
| 설정이 없나? | 파일 열어봄 | 있음 → 아님 |
| 순서가 밀렸나? | 맨 위로 올림 | 여전히 실패 → 아님 |
| 비밀번호 방식이 문제? | 아예 비번 없이(trust) 바꿈 | 여전히 실패 → 아님 |
| 주소 범위가 좁나? | 전체 허용으로 확대 | 여전히 실패 → 아님 |
| 네트워크 문제? | **db1이 자기 자신한테 접속** | 이것도 실패! |

마지막 검증이 결정적이었다. **db1이 자기 자신한테 접속해도 거부**된다면, 네트워크도 db2도 문제가 아니다. **db1의 설정 파일 자체가 문제**라는 게 확정된다.

**진짜 원인:** 파일을 `sed` 명령으로 여러 번 고치는 과정에서, 눈에 안 보이는 손상이 쌓였다.

**해결:** 파일을 조금씩 고치지 말고 **처음부터 통째로 새로 썼다.** 그랬더니 바로 됐다.

**배운 것:** "설정은 분명히 맞는데 안 된다" → 설정 내용이 아니라 **파일 자체를 의심**한다.

### 사고 2. 실수로 원본 데이터를 지움

**무슨 일이:** db1에 SSH로 접속한 상태에서, db2에서 실행하려던 명령 묶음을 그대로 붙여넣었다. 그중에 "데이터 폴더 비우기" 명령이 있었고, 그게 **db1에서 실행되어 원본 데이터가 삭제**됐다.

**왜 그랬나:**
- 여러 줄 명령을 한 번에 붙여넣었다
- 중간의 `exit`(빠져나가기)가 제대로 안 먹었다
- **지금 어느 서버에 있는지 확인을 안 했다**

**복구:** 실습 단계라 중요한 데이터가 없어서, db1을 처음부터 다시 만들었다(initdb). 30분이면 됐다.

**배운 것 (실무에서 제일 중요):**
1. 위험한 명령 전에 **`hostname`으로 지금 어느 서버인지 확인**한다
2. **여러 줄 명령을 한 번에 붙여넣지 않는다**
3. 이 사고를 계기로, Ansible 코드에 **"이미 설정된 서버면 지우는 작업을 건너뛰기"** 안전장치를 넣었다

마지막이 중요하다. 사고를 겪고 → 원인을 알고 → **다시 안 일어나게 코드로 막았다.** 이게 실무에서 하는 일이다.

### 확인 질문
- "설정이 맞는데 안 된다" 상황에서 어떻게 범위를 좁혔나?
- 데이터를 실수로 지운 뒤, 같은 실수를 막으려고 코드에 무엇을 추가했나?

## 6장. 자동 백업 — 복제가 있는데 왜 또 백업하나

### 제일 먼저 알아야 할 것: 복제는 백업이 아니다

4장에서 db1의 데이터가 db2로 자동 복사되게 만들었다. 그럼 db2가 백업 아닌가? **아니다.** 이번 주에 직접 증명했다.

| 한 일 | 결과 |
|---|---|
| db1에서 `DROP TABLE repltest` (실수로 지웠다고 가정) | db1에서 사라짐 |
| db2에서 조회 | **db2에서도 사라짐** |

복제는 db1이 하는 일을 **그대로 따라한다.** 데이터를 넣으면 따라 넣고, 지우면 따라 지운다. 실수까지 충실하게 따라한다.

그래서 역할이 다르다.
- **복제**: 서버가 **고장 났을 때** 대비 → 사본 서버로 넘어가면 됨
- **백업**: 사람이 **실수했을 때** 대비 → 과거 시점의 사본에서 되살림

비유하면 복제는 "실시간으로 똑같이 따라 쓰는 공책", 백업은 "매일 밤 찍어둔 사진"이다. 공책에서 한 페이지를 찢으면 따라 쓰는 공책도 찢긴다. 그때 필요한 게 어젯밤 사진이다.

### 어떻게 만들었나

**① 백업 스크립트** — 실제로 백업을 뜨는 명령 묶음
- DB 내용을 파일로 저장 (`pg_dump`)
- 계정 정보도 따로 저장 (`pg_dumpall --globals-only`) — pg_dump는 DB 안의 데이터만 뜨고, 계정은 DB 바깥에 있어서 따로 떠야 함
- 7일 지난 백업은 자동 삭제 — 안 그러면 디스크가 결국 꽉 참

**② 매일 새벽 3시에 자동 실행** — systemd timer 사용

**③ 백업은 db2(사본)에서 뜬다** — 백업은 DB 전체를 읽느라 무겁다. 원본(db1)에서 뜨면 손님 요청 처리가 느려진다. 사본에서 뜨면 원본은 영향이 없다.

### cron 대신 systemd timer를 쓴 이유

둘 다 "정해진 시간에 자동 실행"하는 도구다. 차이는 이거다.

| | cron | systemd timer |
|---|---|---|
| 새벽 3시에 서버가 꺼져 있었다면 | 그냥 건너뜀 | **켜진 뒤 따라잡아서 실행** |
| 실행 기록 | 따로 챙겨야 함 | `journalctl`로 바로 확인 |

우리 VM은 자주 꺼져 있으니까 "놓친 백업을 따라잡는" 기능(`Persistent=true`)이 중요했다.

timer와 service는 한 쌍이다.
- **timer** = 알람시계 ("언제")
- **service** = 알람이 울리면 할 일 ("무엇을")

알람시계(timer)만 켜두면, 시간이 될 때 service를 깨운다.

### 스크립트에서 중요한 한 줄

```bash
set -euo pipefail
```

"중간에 하나라도 실패하면 즉시 멈춰라"는 뜻이다. 이게 없으면 백업이 실패해도 스크립트가 "성공"으로 끝난다. 그러면 **깨진 백업을 멀쩡한 줄 알고 믿게 된다.** 막상 복구하려는 순간에 백업이 없다는 걸 알게 되는, 가장 최악의 상황이다.

### 복구 리허설 — 백업은 되살려봐야 안다

"백업은 복구해보기 전까진 백업이 아니다"라는 말이 있다. 파일이 있다고 해서 그걸로 진짜 되살릴 수 있는지는 모르기 때문이다. 그래서 실제로 해봤다.

1. **백업 안에 그 테이블이 있는지 먼저 확인** — 없는 걸 지우면 끝이니까, 지우기 전에 확인
2. db1에서 테이블 삭제 → db2에서도 사라진 것 확인
3. 백업 파일을 db2에서 가져와 db1으로 옮김
4. **지운 테이블 하나만 골라서** 복구
5. db1, db2 둘 다에서 데이터가 돌아온 것 확인
6. 임시로 옮긴 백업 파일은 바로 삭제 (DB 데이터가 통째로 들어있으니까)

**왜 테이블 하나만 골라서 복구하나?** 백업은 새벽 3시에 뜬 것이다. 그 뒤로 다른 테이블엔 정상적인 변경이 있었을 수 있다. 백업 전체로 덮어쓰면 그 정상 변경까지 새벽 3시로 되돌아간다. 그래서 **망가진 부분만** 복구한다. 이렇게 하려고 백업을 `-Fc`(골라서 복구 가능한 형식)로 떴다.

**왜 db1에 복구하나?** db2는 읽기만 되는 사본이라 쓰기가 안 된다. db1에 복구하면 → 복제를 타고 db2에도 자동으로 돌아온다. 실제로 그렇게 됐다.

### 아직 부족한 점 (스스로 알고 있어야 함)

- **백업이 db2 안에만 있다.** db2 디스크가 망가지면 백업도 같이 날아간다. 실무에선 다른 서버나 다른 장소에도 복사해 둔다.
- **새벽 3시 이후 변경은 못 살린다.** 오후 2시에 실수했다면, 새벽 3시~오후 2시 사이 데이터는 잃는다. 이걸 해결하려면 "WAL 아카이빙"이라는 더 정교한 방식이 필요하다.

면접에서 "개선한다면?"이라고 물으면 이 두 개를 말하면 된다. 한계를 스스로 아는 것도 실력이다.

### 이번 주에 겪은 실수

**Vault 때문에 전혀 상관없는 플레이북이 멈춤**
3주차에 비밀번호 파일(`group_vars/db.yml`)을 암호화했다. db2는 db 그룹이라 Ansible이 실행될 때마다 이 파일을 **자동으로 읽는다.** 백업 롤은 비밀번호를 안 쓰는데도, 파일이 잠겨 있으니 열쇠를 달라며 멈췄다.
→ 열쇠(Vault 비밀번호)를 **리포 밖** 파일(`~/.vault_pass`)에 두고 자동으로 읽게 설정했다. 열쇠를 자물쇠 옆(리포 안)에 두면 잠근 의미가 없다.

**설정 한 줄을 두 번 넣어서 Ansible 전체가 멈춤**
이미 있는 설정을 `>>`(파일 끝에 덧붙이기)로 한 번 더 넣었다. 같은 설정이 두 줄이 되자 Ansible이 설정 파일 자체를 못 읽었다.
→ 파일을 통째로 새로 썼다 (3주차 pg_hba 교훈과 같은 해결법).
→ 배운 것: `>>`는 멱등하지 않다. 두 번 치면 두 줄이 된다. 2장의 "멱등성"이 왜 중요한지 몸으로 겪은 셈이다.
→ 다행히 설정 파일을 못 읽어서 멈춘 덕에, 그 뒤에 쳤던 DROP 명령은 실행되지 않았다.

## 7장. 모니터링 — 서버 7대를 한 화면에서 보기

### 지금까지 뭐가 불편했나

문제가 생기면 매번 이렇게 했다.
- SSH로 서버 접속 → `df -h`로 디스크 확인 → 나가기
- 다른 서버 접속 → 또 확인 → 나가기
- ... 7번 반복

그리고 더 큰 문제: **새벽 3시에 디스크가 꽉 차면 아무도 모른다.** 아침에 출근해서 서비스가 죽어 있는 걸 발견한다.

이번 주는 이 두 가지를 해결했다.
1. 7대 상태를 **한 화면**에서 본다
2. 문제가 생기면 **먼저 알려준다**

### 등장인물 5명

| 이름 | 하는 일 | 비유 |
|---|---|---|
| **node_exporter** | 각 서버에 설치. 자기 상태(CPU/메모리/디스크)를 알려줌 | 각 지점의 직원 |
| **Prometheus** | 7대를 돌며 상태를 수집하고 저장 | 본사 감사팀 |
| **Grafana** | 수집된 걸 그래프로 보여줌 | 상황판 |
| **Alertmanager** | 문제 생기면 알림 전달 | 비상 연락망 |
| **Loki + Promtail** | 로그를 모으고 저장 | 일지 수집 |

mon이라는 서버(.50)를 새로 만들어서 Prometheus·Grafana·Alertmanager·Loki를 몰아 설치했고, node_exporter와 Promtail은 7대 전부에 깔았다.

### Prometheus는 "가지러 간다" (중요)

여기서 헷갈리기 쉬운 게 방향이다.

**Prometheus는 각 서버가 보내주는 걸 받는 게 아니라, 15초마다 직접 가지러 간다.** 각 서버의 node_exporter가 `http://서버:9100/metrics`에 상태를 차려놓으면, Prometheus가 주기적으로 긁어온다.

**왜 이게 좋은가:** 만약 서버가 보내주는 방식이면, 데이터가 안 올 때 "보낼 게 없는 건지, 서버가 죽은 건지" 모른다. 가지러 가는 방식은 **가지러 갔다가 실패하면 그 자체가 "서버 다운"** 신호다. 그래서 `NodeDown` 알림을 만들 수 있다.

반대로 **로그는 각 서버가 밀어 보낸다(Promtail → Loki).** 로그는 계속 쏟아지는 흐름이라 발생할 때마다 보내는 게 자연스럽기 때문이다. 성격에 따라 방향이 다르다.

### 설정을 손으로 안 적은 부분

Prometheus 설정에 감시할 서버 7개 주소를 적어야 하는데, 손으로 안 적고 **인벤토리에서 자동으로 끌어오게** 했다.

```
{% for host in groups['all'] %}
  - targets: ['{{ IP }}:9100']
{% endfor %}
```

**왜:** 손으로 적으면 나중에 서버를 추가할 때 두 군데(인벤토리 + 감시 설정)를 고쳐야 한다. 하나 빼먹으면 **그 서버만 조용히 감시에서 빠진다.** 이렇게 해두면 인벤토리에 한 줄 추가하고 플레이북만 돌리면 끝이다.

### 알림 — PENDING과 FIRING

알림 규칙은 이렇게 생겼다.

```
alert: DiskSpaceLow
expr: 여유 공간 < 20%
for: 2m
```

여기서 `for: 2m`이 중요하다. **"2분 동안 계속 그래야" 알림을 낸다**는 뜻이다.

그래서 상태가 두 단계로 나뉜다.
- **PENDING**: 조건은 맞는데 아직 2분이 안 됨 (지켜보는 중)
- **FIRING**: 2분 넘게 지속됨 (진짜 알림)

**왜 바로 알리지 않나:** 순간적으로 잠깐 튀는 값에 매번 알림이 오면, 사람들이 알림을 무시하게 된다. 그러면 진짜 장애 알림도 놓친다. 이걸 **알림 피로**라고 한다. 2분 조건이 그걸 막는다.

### 직접 터뜨려본 것 (이번 주 핵심)

"알림을 설정했다"와 "알림이 온다"는 다르다. 규칙에 오타가 있을 수도, 연결이 안 됐을 수도 있다. 그래서 **일부러 터뜨렸다.**

1. web2에 13GB 파일을 만들어 디스크를 90%까지 채움 (여유 10.9%)
2. Prometheus 화면에서 `DiskSpaceLow`가 **초록 → 주황(PENDING)** 으로 변함
3. 2분 뒤 **빨강(FIRING)** 으로 변함
4. Alertmanager를 확인하니 알림이 도착해 있었고, 내용이 **"web2 disk below 20% free"** 였다 — 어느 서버인지 이름이 자동으로 박혀 있음
5. 파일을 지우니 몇 분 뒤 알림이 **저절로 사라짐**

발화만이 아니라 **자동 해제까지** 확인한 게 중요하다. 문제가 풀리면 알림도 꺼져야 정상이다.

### 로그 — 메트릭으로는 모르는 것

메트릭은 "디스크가 90%다"를 알려준다. 하지만 **"왜 그렇게 됐는지"는 모른다.** 그건 로그를 봐야 안다.

Loki를 쓰면 Grafana에서 이렇게 조회할 수 있다.
```
{host="web1"}                          ← web1의 모든 로그
{host="lb1", unit="haproxy.service"}   ← lb1의 haproxy 로그만
{job="systemd-journal"} |= "error"     ← 7대 전체에서 error 포함된 것만
```

마지막 줄이 특히 의미 있다. 예전 같으면 **7대에 각각 SSH 들어가서 grep**해야 했던 걸 쿼리 한 줄로 한다.

**왜 ELK가 아니라 Loki인가:** ELK(Elasticsearch)는 로그 내용을 전부 색인해서 검색이 강력하지만 무겁다(메모리를 많이 먹는다). Loki는 "어느 서버, 어느 서비스" 같은 **꼬리표만 색인**하고 본문은 압축해 둔다. 가볍고, Grafana와 같은 회사 제품이라 잘 붙는다. VM 환경엔 Loki가 맞다.

### 이번 주에 막힌 것

**Loki가 안 켜짐 — 포트 충돌**
Loki를 켜니 계속 죽었다. 로그를 보니 한 줄이 답을 줬다.
```
listen tcp :9095: bind: address already in use
```
Loki와 Promtail이 **둘 다 9095 포트를 기본으로 쓴다**(같은 회사 제품이라). mon 서버에 둘 다 깔려 있으니 먼저 켜진 Promtail이 그 포트를 차지하고 있었다.
→ Loki는 9096으로 옮기고, Promtail은 그 포트를 아예 안 쓰게 껐다. Promtail은 보내기만 하고 받을 일이 없어서 꺼도 된다.

**Grafana에 Loki가 안 보임**
데이터소스 목록에 Loki가 없었다. Grafana를 재시작해도 그대로였다.
→ 대상 서버의 **실제 파일을 확인**하니 Loki 항목이 아예 없었다. Grafana 문제가 아니라 **파일이 배포가 안 된 것**이었다. 플레이북을 다시 돌리니 해결.
→ 배운 것: "설정이 적용 안 됐다" 싶을 때, 재시작부터 하지 말고 **파일이 실제로 있는지부터** 확인한다.

**haproxy 로그가 안 보임 — 이건 장애가 아니었다**
로그 라벨 목록에 haproxy가 없었다. 알고 보니 최근 12시간 동안 haproxy가 로그를 한 줄도 안 남긴 것뿐이었다(잘 돌고 있어서).
→ haproxy를 재시작하니 바로 나타났다.
→ 배운 것: **메트릭은 아무 일 없어도 값이 계속 찍히지만, 로그는 일이 있어야 생긴다.** 로그가 안 보이는 게 항상 고장은 아니다.

### 아직 부족한 점

- **알림이 실제로 전송되지는 않는다.** Alertmanager까지는 도착하는데, 이메일이나 Slack으로 보내는 설정은 안 했다(실습 환경이라 메일 서버가 없다). 운영이라면 Slack 웹훅을 연결하면 된다.
- **mon 서버가 죽으면 관측이 전부 멈춘다.** 감시하는 쪽이 단일 장애점이다.
- **시스템 지표만 본다.** CPU·메모리·디스크는 보지만, "HAProxy가 초당 몇 건 처리하는지", "DB 복제가 몇 초 밀렸는지"는 아직 안 본다. 전용 exporter를 추가하면 가능하다.

## 8장. 방화벽 — 누구에게 열려 있나

### 지금까지 뭐가 문제였나

각 서비스를 만들 때마다 "포트를 열었다". 웹은 80번, DB는 5432번, 모니터링은 9100번.

그런데 **누구에게 열었는지는 생각을 안 했다.** 전부 "아무나 접근 가능"으로 열려 있었다.

예를 들어 web1의 80번 포트. 사용자는 대표 주소(VIP)로 들어와서 로드밸런서를 거치니까, **web1에 직접 접근할 사람은 로드밸런서 둘뿐**이다. 그런데 누구나 접근할 수 있게 열려 있었다.

### 열려 있던 것들을 전부 조사

명령 하나로 7대의 방화벽 상태를 전부 뽑아봤다. 세 가지 문제가 나왔다.

**1. cockpit** — 우리가 안 쓰는 리눅스 웹 관리 도구가 전 노드에 열려 있었다. Rocky 기본 설정이다. 게다가 9090 포트를 쓰는데, Prometheus도 9090이라 겹친다.

**2. db2에서 nginx가 돌고 있었다** — DB 서버인데 웹 서버가 떠 있었다. 이유를 추적해보니, db2를 만들 때 **web2를 복제**해서 nginx가 딸려온 것이었다. 클론의 부작용이다.

**3. db1과 db2가 달랐다** — db1만 DB 포트가 열려 있고 db2는 안 열려 있었다. 지금은 문제없지만, 나중에 db2가 primary로 승격되면 아무도 접근을 못 한다.

### 고친 방식: "누구에게" 를 명시

방화벽 규칙을 이렇게 바꿨다.

```
(이전) 80번 포트를 연다              → 아무나 접근 가능
(이후) 192.168.56.21에서 오는 80번만 → lb1만 접근 가능
```

최종 정책은 이렇다.

| 대상 | 누구만 접근 가능 |
|---|---|
| web의 80 | 로드밸런서 2대 |
| DB의 5432 | DB 서버끼리만 |
| 모든 노드의 9100 | 모니터링 서버만 |
| LB의 8404(상태화면) | 관리용 PC만 |
| LB의 80 | 제한 없음 (여기가 진입점이니까) |
| Grafana 3000 | 제한 없음 (브라우저로 봐야 하니까) |

### 순서가 중요했다

각 항목마다 **"새 규칙 추가 → 기존 개방 제거"** 순서로 했다.

반대로 하면? 잠깐이지만 아무도 접근 못 하는 구간이 생긴다. 그 사이에 Prometheus가 수집에 실패해서 "노드 다운" 알림이 잘못 울릴 수도 있다.

### 절대 건드리면 안 되는 것

**SSH는 손대지 않았다.** SSH가 막히면 Ansible이 서버에 접속을 못 한다. 그러면 **되돌릴 방법도 없다.** VM 화면을 하나씩 열어서 7대를 수동으로 고쳐야 한다.

방화벽 작업의 제1 원칙이다: 자기가 들어가는 문은 잠그지 않는다.

### 적용 후 반드시 검증

방화벽을 좁히면 "막혔는데 서비스가 멀쩡한지" 확인해야 한다. 4가지를 봤다.

| 확인 | 결과 |
|---|---|
| VIP로 서비스 접속 | 정상 (web1/web2 교대) |
| web에 직접 접속 | **차단됨** — 의도한 결과 |
| DB 복제 | 유지 |
| 모니터링 수집 | 7/7 정상 |

"차단됐는데 서비스는 멀쩡하다"가 목표였고, 그대로 됐다.

### 확인 질문
- 포트를 "열었다/닫았다"와 "누구에게 열었다"는 뭐가 다른가?
- 왜 새 규칙을 먼저 추가하고 기존 개방을 나중에 제거했나?
- db2에 nginx가 왜 있었나?

## 9장. 마지막 점검 — 정말 재현되는가

### "재현 가능하다"는 말의 무게

이 프로젝트의 핵심 주장은 **"플레이북만 돌리면 똑같이 만들어진다"**이다. 그런데 정말 그런지 확인한 적이 없었다. 만들 때 한 번씩 돌려본 게 전부다.

그래서 마지막에 **전체를 처음부터 다시 돌려봤다.** 그리고 버그가 두 개 나왔다.

### 버그 1: 두 번째 실행부터 실패하는 코드

DB 플레이북이 이 에러로 멈췄다.
```
Sorry, no shrinking of pglv to 0 permitted.
```

원인: 디스크 볼륨을 만들 때 **"남은 공간 전부를 써라"**라고 적어놨다. 처음엔 맞다. 그런데 두 번째 실행하면 이미 전부 썼으니 "남은 공간 = 0"이고, "0으로 줄이라는 거냐"며 거부한다.

→ "볼륨이 이미 있으면 건너뛰기"를 추가해서 해결.

**최초 구축이 성공했다고 재현 가능한 게 아니다.** 두 번 돌려봐야 안다.

### 버그 2: 두 코드가 서로 싸우고 있었다

더 흥미로운 버그다. 실행 결과를 보니 이런 게 있었다.

```
monitoring.yml → "9100 포트를 연다"      (changed)
firewall.yml   → "9100 포트를 닫는다"    (changed)
```

**같은 포트를 한쪽은 열고 한쪽은 닫고 있었다.** 돌릴 때마다 열었다 닫았다 반복이다.

왜 이렇게 됐나: 5주차에 모니터링을 만들 때 "9100 열기"를 넣었고, 6주차에 방화벽 정책을 만들면서 "9100은 모니터링 서버만 허용"으로 바꾸며 기존 개방을 닫게 했다. 둘 다 살아 있으니 충돌.

이걸 **설정 드리프트**라고 한다. 어느 걸 마지막에 돌리느냐에 따라 최종 상태가 달라지는 불안정한 상태다.

→ 서비스 코드에서 방화벽 부분을 전부 빼고, **방화벽은 방화벽 코드만 담당**하게 정리.

**교훈: 하나의 설정은 한 곳에서만 관리한다.**

### 고친 뒤 결과

다시 전체를 돌렸더니:

```
monitoring.yml : 전 노드 changed=0
firewall.yml   : 전 노드 changed=0
```

**changed가 0이라는 건 "바꿀 게 하나도 없다"는 뜻이다.** 즉 지금 서버 상태가 코드에 적힌 것과 완전히 똑같다. 몇 번을 돌려도 아무 일도 안 일어난다.

이게 2장에서 배운 멱등성이 완성된 모습이고, "재현 가능하다"의 진짜 증거다.

### 확인 질문
- `changed=0`이 왜 좋은 결과인가?
- "처음 만들 때 성공했다"와 "재현 가능하다"는 왜 다른가?
- 두 코드가 같은 포트를 반대로 관리하면 무슨 문제가 생기나?
